# 八大模块技术选型判断

用于客户访谈完成后的方案比较。比较的单位是完整组合，别只比较框架名称。下面是判断方向，不是强制规则。

## 先淘汰不满足硬条件的路线

| 客户事实 | 优先比较的路线 | 重点核对 |
|---|---|---|
| 产品、文章经常由非技术人员编辑；主要靠询盘成交 | WordPress 等一体式 CMS 与合适的托管 CMS | 编辑体验、内容字段、插件依赖、维护人员 |
| 少量公开页面，更新少，有开发者负责 | 静态生成工具/框架与合适的托管平台 | 谁发内容、构建更新、预览与表单服务 |
| 内容营销站，视觉与可视化编辑优先 | 托管建站平台与自托管 CMS | 类目/多语言能力、导出限制、长期费用 |
| 复杂登录、客户专属价、配置器、多个系统共用数据 | 应用框架＋合适后端；必要时 Headless CMS | 权限、数据模型、接口、开发与运维预算 |
| 需稳定的标准下单、支付、库存流程 | 电商平台与 CMS 电商方案 | B2B 客户层级、报价/账期、MOQ、运费、ERP；核对当前套餐 |
| 已有流量/询盘，客户只要求改版 | 先评估现有平台内改进 | URL、索引、转化基线和迁移成本；不因“技术旧”直接换栈 |

平台可重叠：WordPress 可以只当 Headless 后台；Next.js 也能做简单站；SaaS 可能包含 CMS。根据客户条件判断是否值得承担复杂度。客户明确选定平台时尊重选择，不重新发起泛泛的技术辩论。

## 八大模块输出表

| 模块 | 必须落下的选择 | 解释与检查 |
|---|---|---|
| 1 业务与路线 | 询盘/交易/混合；一体/前后分离；建站系统 | 买家要完成什么、后台谁用；一个主方案与一个备选 |
| 2 内容与数据 | 产品/分类/应用/案例模型；CMS；数据库与媒体；搜索与集成 | 字段、关联、批量导入、数据来源；复用已有系统，不重复建库 |
| 3 前端与交互 | 模板/组件；手机布局；筛选、比较、配置等必要交互 | 页面数量不等于模板数量；交互由采购任务决定 |
| 4 渲染与更新 | 各页 SSR/SSG/ISR/CSR 或组合；缓存与发布触发 | 首份、命中、未命中、更新和失败；私人数据不进入公共缓存 |
| 5 部署与性能 | 主机/运行环境、区域、明确的 CDN 接入与缓存规则、媒体策略 | 按 [CDN 规范](cdn-plan.md) 单列接入与规则表，分别选源站与 CDN；欧洲源站非强制；检查命中/未命中/动态链路 |
| 6 搜索与语言 | URL、索引、页面职责、语言与站点关系 | 单语言/多语言、单站/多站、旧 URL；避免自动量产重复页 |
| 7 询盘与衡量 | 表单工具与保存、SMTP/API、企业收件箱、客服/CRM、来源 | 明确 From/Reply-To、域名发信验证、客服排班与离线处理；提交成功不等于收到通知 |
| 8 安全与维护 | 权限、校验、防垃圾、备份恢复、发布/回滚、监控与所有权 | 代码、数据库、媒体分别考虑；总成本包含人的工作 |

## 渲染选型的解释模板

不要只写“SSR＋缓存”，用一个代表页面说明：

> 产品页的资料由谁维护？第一份 HTML 在何时生成？后续访问能复用什么？运营改了一个参数后，怎样让产品页、类目页及相关语言页获得新版？失败时访客看到什么？询盘提交走什么不缓存的接口？

| 方式 | 常见生成时机 | 更新与失效要点 |
|---|---|---|
| WordPress 动态页面＋整页缓存 | 缓存缺失时由服务端生成；也可预热 | 发布时清除/重建相关缓存；后台、表单提交和私人内容按实际规则绕过。不是所有 WordPress “缓存”都是整页缓存 |
| SSG | 构建时生成 HTML | 内容变更触发构建与发布；可由 CMS 自动通知。重建范围与耗时依工具而定 |
| ISR | 构建或访问时生成可复用页面，再按规则更新 | 核对运行环境支持；区分时间与事件触发、旧内容可见窗口及失败保留。不是必然定时执行 |
| 请求时 SSR | 收到请求后在服务端生成 HTML | 是否新鲜取决于数据和缓存规则；按用户生成的结果不可错误共享 |
| CSR/局部交互 | 浏览器取得数据后组装或更新界面 | 适合筛选、后台、选型器；公开核心内容的抓取另验证。服务端生成页面也可以有交互 |

不按名词判断速度胜负。比较缓存命中、未命中、更新后的访问、图片脚本负载和真实地区体验。表单可与静态公开页面并存。

CDN 像分仓，源站像总仓：副本命中时可就近交付；没命中要回源；询盘、登录、后台等通常仍依赖实际服务端。Cloudflare 普通 CDN 默认不缓存 HTML，公开整页缓存需要另行配置，不能说接入后整个网站就自动在边缘交付。新站主要买家在欧洲时可优先比较欧洲源站；已有稳定的其他区域源站，先测实际链路再决定迁移。

## 主方案与备选怎么说

用“因为 A、B，所以选 X；代价是 C；如果条件变为 D，改选 Y”。例如：

> 两名运营要自己更新数百个产品，需求以目录和询盘为主，因此选一体式 CMS。代价是需要维护系统与插件。如果后续出现复杂客户权限和实时配置报价，重新比较应用框架或前后台分离。

一个变化不必立即重构；先评估在现有组合中扩展的成本。预算不足或交期冲突时明确第一阶段范围，而不是推荐无法维护的完整系统。
