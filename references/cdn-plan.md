# CDN 选择、接入与缓存配置

所有方案均读取并输出本配置。客户不必懂 CDN 术语，Codex 根据市场、当前主机/平台、更新频率、动态功能和预算作出选择；复用访谈信息。现有站先区分观察到的现状和拟定改动。

## 1. 明确选哪家、为什么

选定一个主方案，可给一个必要的备选：托管平台自带 CDN、Cloudflare 或其他适合实际平台的服务。说明当前是否已包含 CDN、目标市场、整页/资源缓存需求、更新接口、维护权限、套餐限制与续费；没有当前价格就不造数。不能所有项目固定选择 Cloudflare，也不能在托管已经有完善边缘交付时无理由叠加第二层。

源站位置与 CDN 分开列。WordPress 仍需 PHP/数据库运行环境；新站欧洲客户可优先比较欧洲源站，其他区域现有稳定托管先测再决定。普通 CDN 节点通常自动调度，不承诺固定某个城市节点；特定区域或数据驻留要求另查实际产品支持，不能用源站在欧洲代替合规判断。

## 2. 交付接入表

至少明确以下字段，未知真实值用可替换占位符并标明：

| 项目 | 方案必须写清 |
|---|---|
| 服务与套餐 | 选定供应商/内置服务、理由、费用和权限的已核/待核状态 |
| 源站 | 运行环境、区域、源站主机名或地址的负责人；不公开敏感内部配置 |
| 域名 | 哪个主域/www/资源子域接入，哪个是规范域名；已有域名保持策略 |
| 接入方式 | 平台内置绑定、DNS/代理、服务支持的 CNAME，或资源 URL 接入；选一种适合现状的具体做法 |
| TLS | 浏览器到 CDN、CDN 到源站如何加密与验证，源站证书条件 |
| 邮件与其他服务 | 哪些记录保持原样，防止改 DNS 破坏企业邮箱或验证 |
| 规则维护 | 控制台/配置文件/API 由谁维护，账号归公司，密钥不写入方案 |
| 节点与源站选择 | 自动节点调度与源站区域分开；不把“欧洲用户”写成固定欧洲节点承诺 |

以 Cloudflare 常见全域接入为例：按其当前接入要求将权威 DNS 接入，网站 A/AAAA/CNAME 记录设为 Proxied；不是只把 DNS 放到 Cloudflare 就一定代理。若是托管内置或服务支持的部分域名/CNAME 接入，按实际能力走，不强制所有客户迁移 Nameserver。

Cloudflare 可在源站有有效匹配证书时使用 Full (strict)，说明条件，不能未检查证书直接承诺可切换。保留 MX、SPF/DKIM/DMARC 和验证记录的正确配置，邮件用途的主机/验证记录按服务要求处理。

全站代理通常可以保持原网页 URL；资源域名方案则需配置 `cdn.example.com` 的回源、证书和页面资源 URL，必要时处理字体 CORS 等。仅增加一个资源域名 DNS 记录，不会自动改写网页里的图片链接。

## 3. 交付具体规则表

禁止只写“缓存静态内容、后台不缓存”。每条至少有：编号/规则名；域名与 URL 范围；请求方法/参数/Cookie 等条件；缓存或绕过动作；边缘 TTL；浏览器 TTL；缓存键；更新方式；执行顺序；适用前提与验证状态。

TTL 是副本有效期，不代表节点一定保留那么久。给当前项目拟定具体数值和原因；未知更新频率时先提出标明假设的初始值，不能把所有设置都空成“待定”。[家具示例](example-furniture.md) 提供一份具体草案，数值不是所有项目的标准。

配置时落实以下边界：
- 明确是 CDN 缓存、主机整页缓存、数据缓存还是浏览器缓存。Cloudflare 普通 CDN 默认不缓存 HTML/JSON；整页缓存另配，不能只开启代理就称已完成。
- 只允许已明确公开、相同 URL 对访客一致的成功内容进入公共缓存；含私人资料、会话或用户特定响应的页面不能因为 URL 看似“产品页”就强制缓存。
- 绕过后台/登录、预览、询盘提交、动态报价/账户/购物车、认证请求及会改变输出的 Cookie 等实际路径和条件；JSON/API 不默认全缓存。表单页是否可缓存要检查动态令牌和 Cookie，没验证时先绕过。
- 请求条件与响应条件分开：普通请求匹配规则不能假装直接匹配任意响应头；使用源站 `Cache-Control`、Cookie 行为及所选平台实际能力保障边界。不能用忽略源站头的全局 Edge TTL 强行覆盖 `private`/`no-store` 或删除会话 Cookie 来凑命中率。
- 缓存键保留域名、语言/路径、会改变页面内容的参数；不一概忽略查询参数。搜索、筛选、预览、登录与个性化参数按业务明确处理。
- UTM/广告参数可在确认不改变服务端内容后按平台能力优化缓存键，但保留浏览器 URL 与归因，不为了缓存删除来源信息。能力未核时，带查询参数的 HTML 可暂时绕过，并解释命中率代价。
- 说明哪些规则会重叠，以及哪条最终生效。Cloudflare Cache Rules 相同设置冲突时最后匹配的值生效：允许规则在前、最终绕过保护在后是一种做法，还应让允许条件本身排除敏感请求。不能误写成“先命中第一条就结束”。其他 CDN 按实际优先级处理。
- 有文件内容哈希/可靠版本的新 URL 才适合长时间浏览器缓存。覆盖同名图片时 CDN 清缓存无法清掉访客浏览器里的副本，需新 URL/版本或较短浏览器 TTL。
- 第三方 Tidio、统计脚本和邮件走各自服务，本站 CDN 不自动接管它们。公开 URL 中的资源类型、文件大小、错误响应与下载权限按实际平台限制核对。

控制台/表达式/API 字段按当前官方文档核对。方案阶段可给精确自然语言匹配条件与拟定参数；用户要可直接执行配置时才提供已核对语法与项目实际路径，不能把教学伪代码当可部署表达式。

## 4. 内容更新、失败与回退

写明发布产品/类目/案例/翻译时，由哪个集成或负责人清理主机缓存和相关 CDN URL，再必要时预热；同时考虑关联类目、导航、首页模块及语言版本。检查供应商套餐支持的单 URL、标签/前缀等失效方式和频率，不默认所有能力免费可用。带自定义缓存键/请求方法匹配的规则可能影响失效操作，应按当前官方限制验证。

方案给出允许的旧内容窗口和刷新失败处理，例如通知负责人、可执行的手动单 URL 清理与复查；不能把 TTL 当“准点自动重新生成”。记录规则旧版本，故障时先回退或绕过有问题的缓存规则；不随意更改 MX，不用忽略证书校验解决问题。

## 5. 验收计划与实际证据

只规划时写验收步骤；未实施不声称验证通过。获授权实施后检查：

1. 域名确实通过选定 CDN/平台交付，TLS 与主域跳转正确；代理标记不等于缓存命中。
2. 用正常 GET 对代表资源重复访问，查看 CDN 对应的缓存状态、缓存头及内容。Cloudflare 可观察 `CF-Cache-Status`：HIT 是命中，MISS 是当次未命中；DYNAMIC/BYPASS 等结合实际规则解释，不能机械要求绕过页面必须恰好返回 BYPASS。某些 Worker/代理组合不显示这些头时使用平台相应日志。
3. 验证公开页与静态资源，另核后台、登录、预览、参数、语言、Cookie 等不会错取公共副本；不能只拿一张图片的 HIT 当全站通过。
4. 通过已获授权的测试发布确认产品页与关联页刷新；保留更新前后可辨别证据和时间。网页 read-only 审计时只检查可得现状，不为验证而改客户内容。
5. 询盘/发信等按授权测试，并确认不被缓存拦截或重复；无提交授权时交步骤而非实际发送。
6. 分别观察目标地区命中、未命中与动态链路。给出已测路径/地区/条件与限制；没有测量不虚构毫秒、命中率或提速百分比。
