# 插件、邮箱与客服配套

技术方案必须能回答“装什么、接什么服务、谁管理、怎么配、怎样验收”。必需的是业务能力，不是某个品牌插件；不同栈用原生能力、插件、SaaS 或开发实现。先盘点已有主机、邮箱、许可与 CRM，避免重复购买和重复加载脚本。

## 配套清单怎么交

每个项目记录：用途；本期必需/可选/暂缓；具体工具与选定/候选状态；选择原因；关键配置；依赖与冲突；账号所有者/负责人；免费或付费边界与续费；验收；官方资料和实际核实日期。收费服务、插件授权和实施工作费分别写，没有实价就标待核。

客户指定 Tidio 时必须回应其配置和取舍，但不是每个项目都强制开通。报价/方案阶段只规划，不代表允许创建账号、订阅、安装插件、改 DNS 或向真实地址发测试邮件；后续实施按当时授权完成。

## 常见能力与候选

| 能力 | 可比较的具体实现 | 需要落实的配置与取舍 |
|---|---|---|
| 结构化内容 | WordPress 原生内容模型/字段，必要时 ACF 等 | 产品字段、关联、编辑权限、数据导出；不为所有简单字段都加重型插件 |
| 询盘表单与线索保存 | Fluent Forms 等，或所选栈的表单服务/自建接口 | 产品型号、数量、国家、邮箱、需求；保存、去重、防垃圾、成功/失败提示。附件、条件路由与 CRM 集成核对版本和费用 |
| 网站邮件发送 | FluentSMTP 或 WP Mail SMTP 等选一个，连接合适的 SMTP/API 服务 | 认证通道、From、Reply-To、发送记录与失败处理；插件不是企业收件箱，也不等于免费发信服务 |
| 企业邮箱 | 复用现有域名邮箱；需新建时比较 Google Workspace、Microsoft 365、Zoho 等 | 真实业务收件箱、人员账号/别名/共享邮箱、MX、客户端、收发与回复路径；按团队与实际地区可用性比较 |
| 在线客服 | Tidio 官方插件或官方脚本二选一；已有其他系统可复用 | 公司拥有账号，接待人员、工作时段/时区、语言、离线留言、通知、线索归属、移动端显示与脚本性能 |
| SEO 管理 | Yoast SEO 或 Rank Math 等选一套；定制栈可原生实现 | 标题/描述、Sitemap、规范 URL、索引与结构化数据；避免多套工具重复输出同类标记 |
| 多语言 | 按内容模型比较 Polylang、WPML 或相应平台原生方案 | 独立 URL、对应关系、字段/表单/客服语言、审核与更新同步；核对许可及翻译/插件兼容性 |
| 缓存与 CDN | 优先托管内置缓存；配 Cloudflare 等；必要时增加兼容的缓存工具 | 主机与边缘缓存各管什么、命中状态、排除项、发布清缓存；不能默认 Cloudflare 缓存 HTML。若比较 LiteSpeed Cache，其服务端页面缓存能力需核对运行环境 |
| 防垃圾与应用保护 | 表单已有校验/蜜罐/限流，必要时 Turnstile 等 | 真正服务端验证，避免重复验证码；实际试填是否阻碍正常买家 |
| 备份与恢复 | 托管已含备份先复用；不足时比较 UpdraftPlus 等 | 数据库、媒体、配置、保留期限、异地副本、恢复流程；不要重复开多套资源密集的备份 |
| 搜索与转化分析 | Search Console；按需要 GA4、广告转化和同意管理 | 域名验证、事件成功时机、来源参数、去重与有效询盘；避免多个插件重复加载统计代码 |

上表是能力目录，不是每站的强制安装列表。确定具体工具后查当前官方能力、维护/兼容状态、套餐限制；托管平台已覆盖或本期没有必要的项目明确不加。网站不使用 WordPress 时，不套用 WordPress 插件清单。

## 邮箱必须分清三件事

1. **企业邮箱**：业务员实际收发邮件的地方，例如 `sales@example.com`。域名邮箱的收件主要由 MX 指向的服务承接。
2. **网站发信**：网站通过 SMTP/API 通道把询盘通知发给业务员；可以使用合适的企业邮箱通道，也可使用独立事务邮件服务，要核对限制、认证和用途。
3. **域名发信身份**：按实际服务商配置 SPF、DKIM、DMARC，使邮件身份可验证。DNS 由谁托管，与邮箱由谁提供是两回事。

通知示意：

```text
买家表单邮箱：buyer@example.net
From：website@example.com（经发信服务验证的本方发件身份）
To：sales@example.com（实际存在并有人查看的业务收件箱）
Reply-To：buyer@example.net（已做格式校验的买家地址）

业务员在自己的邮箱点“回复” → 收件人应是买家
```

地址均为占位示例。不能把客户随便填写的外部地址设成网站 From；校验格式也不等于证明买家邮箱真实存在。若发买家自动回执，回执的 Reply-To 应是实际有人处理的本方业务邮箱，并配置防滥用与失败处理。

规划配置时要说明：
- MX 按企业邮箱服务商要求保留/调整，不能因为接 CDN 就重置。新增发送服务不一定需要改主域收件 MX；以服务商提供的域名或子域验证方案为准。
- SPF 列出真正获准的发信来源；同一域名不要简单新增多条冲突 SPF。DKIM 使用各服务商给出的记录；DMARC 按身份对齐和报告制定策略，不能随意削弱客户已有配置。
- SMTP/API 的认证方式、服务器/端口或 OAuth、发件身份与验证记录依据当前官方说明；不要在聊天或交付文档记录密钥/密码。
- 迁移 DNS 先清点现有邮件记录。邮件主机及验证 CNAME 的 DNS-only/代理设置按服务商要求；普通 Cloudflare Web 代理不代理 SMTP/IMAP。
- 发信接口返回成功不代表邮件最终进入收件箱；需要结合投递结果、实际收件、垃圾箱与回复路径检查。日志按必要范围保留，避免无限保存含个人信息的完整邮件正文。

实施验收方案：从已获授权的测试表单/地址提交→后台出现唯一线索→发信服务记录投递结果→业务邮箱收到→点回复确认到测试买家→覆盖通知失败时仍保留线索。未获发信/提交授权时，只交测试步骤，不实际对外发送。

## Tidio 等客服系统的配置

先确认谁在什么时段、用什么语言接待，和当前 CRM/业务邮箱如何衔接。有人接待时安排在线窗口；无人时明确离线留言与跟进负责人，不让界面假装真人一直在线。

- 使用客户拥有的账号与站点项目，插件和脚本只接入一份。
- 配置英/德等实际语言的欢迎语、离线提示、位置与手机布局，避免挡住询盘按钮。
- 检查留言是否进入客服收件箱、谁收到提醒、如何进入销售跟进；不能假设聊天工具的联系人已自动写入本站询盘或 CRM。
- AI 机器人是独立可选项；需要批准的知识资料、费用与人工转接机制。普通在线聊天需求不自动等于订阅 AI 套餐。
- 对比接入前后页面负载，按实际需要安排加载与同意控制；聊天是线索入口之一，保留可靠表单。
- 服务配额、坐席、历史记录、自动化和语言能力以当前套餐为准；不把插件目录的营销表述当服务承诺。
